## 1. 新增路由 / 工具与入参

| 入口 | 类型 | 入参 | 返回 |
| --- | --- | --- | --- |
| `github_get_pull` | Agent 工具（只读，timeout 30s） | `repo`（`owner/name`）、`number`（正整数）、`include?`（`files` / `reviews` / `conversation` 数组，默认全取） | 聚合详情（见第 2 节） |
| `GET /api/github-manager/pull` | 面板路由 | `full_name`、`number`、`include?`（逗号分隔） | 同工具，`{ok:true,data}` |
| `GET /api/github-manager/pull-file` | 面板路由 | `full_name`、`number`、`path` | 单个文件的 patch（最多 200 KB 文本） |
| `POST /api/github-manager/token` | 面板路由（同一套 Host/Origin + cookie 准入） | `{token}` | `{storage, persisted, degraded, warning}`，不回显 token |
| `GET /api/github-manager/status` | 既有路由扩展 | — | 新增 `tokenStorage`、`storageWarning` |

命名跟随现有惯例：复数路由用于列表（`/pulls`），单数路由用于单个对象（`/pull`、`/pull-file`），工具用 `github_get_pull`。

## 2. 聚合与降级策略

一次 PR 详情聚合四个 GitHub 端点：

1. `GET /repos/:o/:r/pulls/:n`（锚点，失败直接按真实 HTTP 状态抛出）
2. `GET /repos/:o/:r/pulls/:n/files`：`per_page=100&page=N`，最多 100 个文件；达到上限或 `pull.changed_files` 大于实际取回数时 `files.truncated=true`，顶层 `truncated=true`
3. `GET /repos/:o/:r/pulls/:n/reviews`：`per_page=100`，最多 100 条；每条保留 `author` / `state`（APPROVED、CHANGES_REQUESTED、COMMENTED、DISMISSED、PENDING）/ `submittedAt` / 正文摘要；附 `summary` 计数与 `latestState`
4. `GET /repos/:o/:r/issues/:n/comments`：总数取 `pull.comments`；先取第 1 页，若 `Link rel="last"` 指出后续页则再取最后一页，返回最近 10 条摘要（`conversation.total` / `count` / `truncated`）

聚合结构：

```text
{ repo, number, include, pull, files, reviews, conversation,
  missing: [{ section, code, status, message }],
  partial, truncated }
```

- 三个集合请求并行执行；任一子请求失败只把该 section 置为 `{items:[],count:0,truncated:true,failed:true}`，写入 `missing`，其余区块照常返回，不抛整单错误。
- `partial=true` 表示有任一区块缺失；`truncated=true` 覆盖「文件超上限 / review 超上限 / 对话只给摘要 / 子请求失败」。
- 403 分类（`classifyHttpError`）：`x-ratelimit-remaining: 0`、存在 `retry-after`、或正文含 rate limit → `rate-limit`；否则 → `forbidden`。429 → `rate-limit`，404 → `not-found`，401 → `auth`。限流错误消息附带 `Retry after Ns.` 或 `Limit resets at <ISO>`。
- 超时继续复用 `github()` 的 20s 默认预算与 `requestSignal`。
- diff 不内联：文件对象只给 `path` / `status` / `additions` / `deletions` / `changes` / `patchAvailable` / `patchBytes` / `blobUrl`。点单文件时走 `/pull-file`，只取一个文件的 patch；超过 200,000 字符截断并标 `truncated`；二进制/无 patch 返回 `reason:"no-patch"`，不在列表 100 个文件内返回 `reason:"file-not-found"`。

面板：PR 列表行整体可点（右侧另有「详情」按钮，便于键盘操作），进入后替换列表区显示标题、状态、作者、分支、`+additions / −deletions`、文件数、文件列表（可展开单文件 diff）、review 列表与汇总、最近对话；缺失区块显示 `pullMissing` 提示。中英文案均在 `client.js` 的 `zh` / `en` 字典内。

## 3. token 存储方案与降级

存储位置：`<DSH_HOME>/github-manager/credentials.json`（`DSH_HOME` 缺省 `~/.dsh`；测试/自定义用 `GITHUB_MANAGER_TOKEN_FILE` 覆盖）。

存储记录：

```json
{ "version": 1, "storage": "safeStorage",
  "ciphertext": "<base64>", "updatedAt": "<ISO>" }
```

- 写入：`safeStorage.encryptString(token)` → base64 → 同目录 0600 临时文件 → `rename` 原子替换 → `chmod 0600`；目录 0700。**明文不落盘。**
- 读取：`safeStorage.decryptString(Buffer.from(ciphertext,'base64'))`。
- 解析顺序：env（`GH_TOKEN`/`GITHUB_TOKEN`）→ 本地加密 vault → `gh auth token` → `gh hosts.yml`。本地 vault 只由面板「保存 token」/ `POST /token` 显式写入；env 和 gh 的 token 不会被自动复制落盘。
- `safeStorage.isEncryptionAvailable() === false`（或拿不到 Electron safeStorage）：**只放进程内存**，返回 `storage:"memory-degraded"`、`persisted:false`、`warning:"encryption-unavailable"`，绝不写明文文件；status 带 `storageWarning`，面板顶部显示「凭据存储降级」横幅。
- 旧明文迁移：启动时（`apply`）和首次本地 vault 读取时检查旧记录（`token` / `githubToken` / `oauth_token` 字段）。有加密能力则就地加密 + 原子替换；失败则保留原文件、继续使用该 token、返回 `storage:"plaintext-degraded"` + `warning:"migration-failed"`，不丢凭据。safeStorage 不可用时旧明文文件保持原样，但 status 会带 `encryption-unavailable` 告警。
- token 不进入日志/错误/工具返回：保存响应不回显 token；`GithubError` 只带 HTTP 状态与 GitHub message；新增测试对 status、工具结果、错误对象、保存响应做 `JSON.stringify` 断言。

### 重要环境限制（必须让 lead 知道）

当前桌面端把 Host 进程以 `ELECTRON_RUN_AS_NODE=1` 启动（实测宿主进程 75913）：该进程 `process.versions.electron = 44.7.0`，但 `require('electron')` 抛 `Cannot find module 'electron'`，所以 **当前打包桌面端里 safeStorage 实际不可用**，vault 写入会走 `memory-degraded` 内存路径（有可见提示，不写明文）。要让「加密落盘」在桌面端真正生效，需要 DSH/desktop 侧提供 safeStorage 桥（例如把加密/解密通过 Host 服务暴露给插件）；这不在 `plugins/github-manager` 可写范围内。实现已按「能拿到就加密，拿不到就内存降级」写好，测试用 stub 覆盖两种分支。

## 7. 未做 / 未验证

1. **真实 Electron safeStorage 未在桌面端验证，且当前 Host 进程用不了它**：宿主进程带 `ELECTRON_RUN_AS_NODE=1`，`require('electron')` 直接失败；safeStorage 分支只在 stub 下验证。桌面端当前实际走 `memory-degraded`（不写明文、面板有提示）。需要 DSH/desktop 提供 safeStorage 桥后才能真正加密落盘。
2. **未在真实 GitHub 上打请求**（按契约全离线）；未在运行中的 Web GUI 里点选验证（插件未安装/未重启），面板交互仅由 `.verify-client.mjs` 的静态渲染烟测覆盖，未验证真实点击后的 patch 加载态。
3. 超过前 100 个文件的 diff 无法在面板中展开（文件列表本身已截断）；review 也只取前 100 条。
4. 对话只保证「最后一页 + 最近 10 条」，不是完整线程；无 `Link` 头的极端情况会退化为第一页末尾 10 条。
5. 迁移在 `apply` 启动时触发，失败只告警、保留明文原文件；「迁移成功」用临时目录验证，未在 Windows 上验证 `rename` 覆盖与文件模式（0600 检查在非 win32 才有断言）。
6. token 自动持久化仅限面板显式保存；env / gh CLI 的 token 保持原有语义（不复制落盘）。若 lead 期望「读到 env token 就自动加密存一份」，需要另加产品决策。
