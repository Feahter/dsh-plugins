# 「墨炉」中文提示词设计

实现文件：`src/recipes/novel/prompts/zh.js`
契约来源：`docs/architecture.md` §4.1（参数）、§4.2（阶段）、§4.3（输入预算）、§4.4（输出格式）、§4.5（质量门槛）。

本文只描述提示词层：怎么把引擎给的素材拼成一次高质量调用，以及为什么这样拼。引擎、校验器、重试策略不在本文范围内。

---

## 1. 目标与非目标

**目标**

- 让长篇小说读起来像人写的：有具体感官、有潜台词、有因果、有信息差、有节奏呼吸。
- 十一个阶段各守各的工艺重点，但共享同一套「工艺宪法」，避免越写越像大纲或说明文。
- 输出格式硬约束，JSON 可被引擎直接解析，markdown 可直接落盘。
- 所有输入都在预算内；缺素材时降级而不是抛错。

**非目标**

- 不在这里做事实校验、字数统计、AI 腔计数——那些是 `src/forge/**` 的确定性门槛。
- 不在这里调模型、读文件、写文件、改 `ctx`。
- 不为了「文学性」牺牲可解析性；格式优先于自由发挥。

## 2. 调用契约

```js
export function createPrompts() {
  return { premise, bible, characters, spine, outline, beats, draft, summary, review, revise, blurb }
}
export default createPrompts
```

每个函数都是 `(ctx) => ({ system, user, maxTokens, temperature? })`。

- `ctx` 是引擎的 stage ctx，可用：`params`、`project`、`item`、`items`、`index`、`total`、`has(key)`、`read(key)`、`text(key, maxChars?)`、`json(key)`、`list(path)`、`fit(text, maxChars)`、`log()`。
- 本文件是纯函数：无 import、无 IO、无网络、无模型调用、不修改 `ctx`。
- `summary` 不是独立 stage：它由 `draft` 的 item 在同一章写完后二次调用，保证「第 n 章写作时一定有第 n-1 章摘要」。
- `ctx` 的读取全部做了容错：`has` 抛错、`text` 返回空、`json` 抛错、`list` 返回空数组，都走「素材缺失」分支，不中断流水线。

---

## 3. 结构：宪法 + 附录 + 预算

`system` 由两块拼成：

1. `CRAFT`：共享工艺宪法。12 条硬约束 + 5 条写作时的操作纪律。所有阶段都带。
2. `ADDENDA[stage]`：该阶段的工艺重点和输出纪律。

`user` 由四块拼成：

1. 项目头：书名、类型、读者、视角、章数 × 字数、文风关键词。
2. 带标签的素材段：`【本章细纲】【上一章摘要】【连续性账本】【下一章要发生】【人物速查】【文风样本】`等。
3. 本阶段的写作指令。
4. 输出格式契约：JSON 阶段给「字段表 + 一个最小合法示例」；markdown 阶段给结构约束。

截断策略：

- 普通段落用 `ctx.fit`，超长就截尾并加「（已截断）」。
- 正文类长文（review/revise/summary 的 draft）用 `fitEnds`：保留头尾，避免把结尾钩子砍掉。
- draft 按 §4.3 的优先级：先砍人物速查，再砍账本，最后才 `hardCap` 兜底。
- 所有阶段最后都过一遍 `hardCap`，保证 `user` 不超过该阶段上限。

## 4. 阶段总表

| 函数 | 产物 | 格式 | 主要输入 | maxTokens | temperature | user 上限 |
|---|---|---|---|---|---|---|
| `premise` | `brief` | JSON | premise、genre、audience、tone、styleGuide、seed | 1400 | 0.9 | 6000 |
| `bible` | `bible` | markdown | brief、premise、styleGuide | 3000 | 0.7 | 9000 |
| `characters` | `characters` | JSON | brief、bible | 3200 | 0.85 | 10000 |
| `spine` | `spine` | markdown | brief、bible、characters | 3200 | 0.7 | 11000 |
| `outline` | `outline` + `ledger` | JSON | brief、bible、characters、spine、chapters | `min(12000, max(2200, 1200 + chapters×150))` | 0.6 | 11800 |
| `beats` | `beats/*` | JSON | 本章章节卡、前后章目标、上一章摘要、账本、人物、文风 | 2800 | 0.75 | 10500 |
| `draft` | `draft/*` + `summary/*` | markdown | 本章细纲、上一章摘要、账本、下一章目标、人物、文风 | `min(16000, max(1600, round(words×2.2)))` | 0.9 | 11800 |
| `summary` | `summary/*` | markdown | 本章正文、细纲、上一章摘要 | 900 | 0.2 | 11500 |
| `review` | `review/*` | JSON | 本章正文、细纲、账本、人物、前后章、预期字数 | 4000 | 0.1 | 15000 |
| `revise` | `draft/*` + `summary/*` | markdown | 本章正文 + findings、细纲、账本 | `min(16000, max(1600, round(words×2.2)))` | 0.5 | 17000 |
| `blurb` | `blurb` | markdown | brief、spine、outline、characters | 1400 | 0.85 | 9000 |

说明：

- `outline` 的 24 章默认值 → 4800 tokens；120 章上限 → 12000。
- `draft`/`revise` 的 3000 字默认值 → 6600 tokens；8000 字上限 → 16000（与 §4.3 一致）。
- `summary` 只有 900 tokens，因为它被硬限制在 300 字，不需要更多。
- `review` 从 2600 提到 4000：推理模型会把预算烧在 reasoning 上，2600 时经常返回空正文（`LLM_EMPTY`），见 architecture §6.4 #13。

## 6. 共享工艺宪法

`CRAFT` 是所有阶段复用的 1200+ 字块，包含 12 条硬约束：

1. **视角**：只写视角人物此刻能感知、能想到、能知道的东西；别人的内心只能靠外在信号让读者判断。
2. **场景**：谁想要什么 + 什么挡着 + 局面怎么变 + 带着什么离开；转折必须改变力量、信息或关系。
3. **具体**：不命名情绪，写动作、身体反应、物件变化；细节和利益有关。
4. **对话**：表面谈 A，底下争 B；规矩在违反、利用、付代价时显形。
5. **信息**：每章改变「谁知道什么」；读者、视角人物、对手的信息差要设计。
6. **因果**：结果能追到前文的选择；巧合只能制造麻烦，不能解决麻烦。
7. **节奏**：长短句交替，一段一个意思；该慢舍得多给细节，该快一句带过。
8. **连续性**：事实、时间、伤病、物品、钱、知情范围、关系以账本为准。
9. **反 AI 腔**：删抽象名词、成对形容词、三连排比、警句；不总结主题，不替读者感动。
10. **章节**：开头有当下压力，结尾留具体的、未解决的问题。
11. **欲望**：每个出场人物都有当下想要的东西；没有欲望的人不许出场。
12. **主题**：主题是可被反驳的命题，让人物用各自的下场投票，不让人物说出来。

另加 5 条操作纪律：叙述距离、物件与动作、标点与呼吸、写完自检、词的选择。

**为什么共享**：这 12 条是跨阶段的「品味基线」。如果每阶段各写一套，模型会在阶段切换时丢掉约束；共享块 + 阶段附录的结构，让每个 system 都完整，同时只追加该阶段真正需要的东西。

## 7. 分阶段设计

### 7.1 premise：一句话 → 可生产冲突的承诺

- 输出 `brief` 六字段：`title`、`logline`、`theme`、`promise`、`ending`、`genreTags`。
- logline 必须含：主角 + 处境 + 行动 + 代价，≤60 字，有具体对手或倒计时。
- theme 写成可被反驳的命题，不写「关于爱与救赎」。
- ending 只写落点和代价，不写过程；必须回答主题，并让主角失去不可逆的东西。
- **书名取舍**：契约只有 `title` 一个字段，不能加 `titleCandidates`。因此要求模型在草稿里按「意象／冲突／人称／时间／反讽」各拟一个，共 5 个，比选后只把胜者写进 `title`。这样既不越契约，又保留比选过程。

### 7.2 bible：只写会咬人的设定

- 不是百科：每条设定都要回答「让谁得利、让谁受害、逼人物做什么选择」。
- 只写会反复用到的：3 条硬规则、3–6 个地点、时代日常、禁忌与代价、反复出现的意象与物件。
- 规则必须有边界和代价；地点要有感官锚点和「谁的地盘」。
- 每条规则后写一句「它会逼出什么冲突」。
- 禁止「这是一个充满魔法的大陆」式空话、历史年表、正文里能自己看到的东西。

### 7.3 characters：压力下的预测模型

- 每人八字段：`name`、`role`、`want`、`fear`、`secret`、`voice`、`arc`、`relations`，外加 `gender`。
- `gender` 只能是「男」或「女」，必填：它决定后文用「他」还是「她」。名字不暗示性别时（沈砚、周岩）更要写清；模型漏写时 `characters` 阶段在事件流里记一条 warn，不阻断。
- 新建时可以用 `protagonistGender`（`auto`/`男`/`女`）把主角性别定死，prompt 里会变成硬约束。
- `want` 与 `fear` 必须互相拉扯；`secret` 要能在中段爆炸；`arc` 由事件逼出来，不是顿悟。
- `voice` 承载两句：第一句说话方式（句长／用词／口头禅／沉默时做什么），第二句行为底线（「他会……；绝不会……」）。这样不新增字段，也能给后文对白一个锚。
- 关系不对称：A 以为是朋友，B 只在利用 A。
- 人数 5–7；示例只列 1 人，正文明确提醒「示例是形状示范」。

### 7.4 spine：因为 → 所以 → 终于

- 不是大纲，是因果链：10–15 环，每环「因为【前因】，他选择【行动】，所以【后果】」。
- 三幕（或起承转合）各写：相信什么 → 什么打破 → 付出什么代价 → 变成什么样。
- 每卷一条情绪曲线：读者的情绪从__到__；主角的处境从__到__；本卷不可逆的一件事。
- 结局落点：最后一个画面、最后一句话、主题的回答；必须失去一样再也拿不回来的东西。
- 禁止「经过一系列冒险，他成长了」；禁止巧合解决主线。

### 7.5 outline：每章四件事

- 输出 `outline`（`volumes` + `totalChapters`）与 `ledger`。
- 每章必须有 `goal`、`conflict`、`turn`、`hook`；`turn` 改变力量／信息／关系／时间压力之一；`hook` 必须具体到动作、台词、物件。
- 卷有 `purpose`：这一卷结束时，主角相信的东西必须错一次。
- `cast` 从人物档案里选 1–4 人；需要新角色时用「无名配角」，不给重要新角色起名。
- 章节数精确等于用户要求，`id` 从 `ch01` 连续编号。
- JSON 示例只列 1 卷 1 章，示例后明确写「你的输出必须 3–5 卷、共 N 章」，防止照抄。

### 7.6 beats：5–9 个可拍的场景

- 每场九字段：`no`、`where`、`when`、`cast`、`goal`、`obstacle`、`turn`、`exit`、`sensory`。
- 场景之间因果相连：上一场的 `exit` 是下一场的入口；最后一场的 `exit` 落在本章 `hook` 上。
- `turn` 让局面变好或变坏，不原地打转；`exit` 是人物带着什么离开（决定／伤口／错误／信息）。
- `sensory` 不是「气氛描写」，是一个具体感官锚点（声音／气味／温度／触感／光线），写正文时要用。
- 场数按信息量与情绪重量分配，不平均切；重场戏 2–3 场，过场 1 场带过。
- 示例只列 1 场，正文明确「必须 5–9 场」。

### 7.7 draft：作者，不是助手

- 直接写正文。第一行必须是 `## 第N章 标题`（两个井号、空格、第N章、空格、标题），段落之间空一行。
- 不要前言、总结、解释、小标题、列表、作者按、「以下是本章」。
- 按细纲顺序写；允许为了更强而偏离，但必须兑现本章转折与结尾钩子。
- 结尾停在钩子指向的具体动作、话语或物件上，不写「他陷入了沉思」。
- 目标字数 `wordsPerChapter`，可接受 0.9–1.15 倍；宁少勿注水。
- system 内含 16 条反 AI 腔禁止清单（见 §8）。

### 7.8 summary：给下一章自己的交接单

- ≤300 字，四行四标签：`发生：`、`知情：`、`钩子：`、`时空：`。
- 发生按因果写，不按时间流水；只写正文确实发生的事。
- 知情写「谁从谁那里知道了什么，谁还被蒙着」。
- 钩子写成下一章能直接接手的动作或信息，不写「留下了悬念」。
- 保留专有名词；不评价、不推测、不剧透、不补正文没有的设定。
- 由 draft item 自己调用，保证摘要链不断。

### 7.9 review：责任编辑，不是夸奖者

- 输出严格 JSON：`findings[]` + `ledgerPatch` + `verdict`。
- 逐项对账：事实、时间线、知情范围、视角越界、AI 腔、节奏、对话信息量。
- 每条 finding 必须有 `where`（第几段／哪句）和 `fix`（怎么改：替换动作、删哪句、补哪个感官细节）。
- `severity`：`block`＝读者会出戏／前后矛盾／关键信息错；`warn`＝明显削弱体验；`note`＝可改可不改。
- `ledgerPatch` 只写本章新增或改变的事实／线索／人物状态／时间线，必须能在正文找到依据。
- `verdict`：有 `block` 或 `warn ≥ 3` → `revise`，否则 `pass`。

### 7.10 revise：外科医生，不是重写者

- 只动 findings 指出的地方；没被点名的段落尽量原样保留。
- 禁止：重写全章、改主线／结局、增删场景、改人物关系、改叙事视角、换文风。
- 允许：替换句子、补一个感官细节、删一句解释、按 finding 调换段落、补一句过渡。
- 每条 finding 都要落地；无法执行的跳过，不把修改说明写进正文。
- 字数与原文相差不超过 10%；仍以 `## 第N章 标题` 开头，段落空行。
- 输出完整正文，不只给片段，不解释改了什么。

### 7.11 blurb：封面文案

- 书名定稿：从 premise 的 `title` 继承；需要时可以给一个更准的，但只输出一个。
- 一句话卖点：谁 + 想要什么 + 被什么挡住 + 最大的代价，不剧透结局。
- 300 字简介：只写第一幕的压力和选择，停在抉择前；不写结局、不写反转、不写「最终他明白了……」。
- 标签 4–6 个：类型 + 核心设定 + 情绪，不堆热词。
- 不写「本书讲述了」式说明文；用封面文案的语感。

## 8. 反 AI 腔清单（16 条）

这张表同时存在于 `draft` 的 system 和本文档，改一处必须同步另一处。

| # | AI 写法 | 改成什么 | 示例 |
|---:|---|---|---|
| 1 | 仿佛／似乎／像是 | 具体观察或身体反应 | 仿佛有人看他 → 后颈汗毛立起来 |
| 2 | 不禁／不由得 | 删掉，直接写动作 | 不由得后退一步 → 后退一步，鞋跟撞上门槛 |
| 3 | 缓缓／微微／轻轻 | 给速度、幅度或声音 | 缓缓抬头 → 抬头，脖颈响了一声 |
| 4 | 一丝／一抹／几分 | 换成看得见的东西 | 一丝笑意 → 嘴角动了一下，很快压回去 |
| 5 | 眼中闪过／嘴角勾起 | 一个动作或一句台词 | 眼中闪过慌乱 → 茶杯放回桌上，放得太重 |
| 6 | 空气仿佛凝固 | 在场者的具体反应 | 没人接话，挂钟走了三格 |
| 7 | 心中五味杂陈 | 一个自相矛盾的动作 | 想笑，喉咙里出来的却是一声咳嗽 |
| 8 | 莫名的／难以言喻的 | 来源不明但具体的细节 | 莫名不安 → 他把钥匙数了三遍 |
| 9 | 他知道／她明白 + 解释 | 把认知变成决定或动作 | 他知道不能再等 → 他按灭烟，拿起外套 |
| 10 | 不是 A，而是 B | 直接写 B | 不是愤怒，是恐惧 → 他的手抖得扣不上扣子 |
| 11 | 三连排比／抽象名词堆叠 | 只留最具体的一项 | 孤独、绝望、无助 → 他把电视开着，声音调到最小 |
| 12 | 与此同时／在城市的另一端 | 删掉全知切换，回到视角人物眼前 | — |
| 13 | 他感到／她意识到 + 抽象名词 | 写感官证据 | 她感到危险 → 声控灯一层层亮上来，没人说话 |
| 14 | 形容词堆叠 | 让一个动词承担 | 冰冷而锋利的目光 → 他看她那一眼，像在估价 |
| 15 | 章末总结／抒情 | 落回具体动作或物件 | 这一夜注定无眠 → 天快亮时，烟灰缸满了 |
| 16 | 对话讲设定 | 让规矩在冲突里显形 | 「你也知道规矩……」 → 他把刀放上桌：要么破例，要么收尸 |

**执行原则**：不是「少用」，是「命中就换」。清单里的词不是风格偏好，是模型腔的指纹；保留一个，读者就会从故事里掉出来一次。

## 9. 好段落 vs AI 段落

### 好段落（约 120 字）

> 老周把登记簿翻到最后一页，指腹在墨迹上停住。那三个字是他的笔迹，横折却比他平时多拐了一下。他合上本子，又打开，纸角蹭过指缝，发出很轻的一声。灯没开，他把手电夹在腋下，光柱扫过一排冷藏柜，编号从 03 跳到 05，中间空着一个。走廊尽头的冰柜嗡了一下，像有人在里面翻了个身。

### AI 段落（约 120 字）

> 夜色深沉，空气仿佛凝固了。老周缓缓翻开登记簿，眼中闪过一丝难以言喻的恐惧。他不禁后退一步，心中五味杂陈。与此同时，走廊尽头传来一阵莫名的声响，仿佛在预示着什么。他深吸一口气，努力让自己平静下来，却发现自己根本做不到。他知道，这一切似乎才刚刚开始。他不敢回头，也不敢出声。

### 差在哪

| 维度 | 好段落 | AI 段落 |
|---|---|---|
| 情绪 | 不命名，用「指腹停住」「又打开」承载迟疑 | 直接报「恐惧」「五味杂陈」 |
| 感官 | 纸角蹭指缝、冰柜嗡一声，来源明确 | 「夜色深沉」「空气凝固」是套话，没有来源 |
| 信息 | 笔迹是他的、横折多拐一下——具体异常，读者自己起疑 | 「预示着什么」空泛，没有可验证的信息 |
| 因果 | 他合上又打开，是因为不敢确认；冰柜声是环境，也是压力 | 后退、响动、开始，彼此没有因果 |
| 结尾 | 一个动作 + 一个声音，钩子具体 | 「似乎才刚刚开始」是预告，不是钩子 |
| 词 | 动词承担画面 | 副词、形容词、比喻堆叠 |

### 10.1 代码内常量

### 10.2 用户参数

| 参数 | 影响 | 注意 |
|---|---|---|
| `premise` | 整个故事的种子 | 8–2000 字；太短会让 premise 阶段空转，太长会挤占风格样本 |

## 11. 已知风险与缓解

| 风险 | 触发条件 | 提示词层缓解 | 残余风险 |
|---|---|---|---|
| 模型不遵守 JSON | 长输出、字段多、示例长 | 只给一个最小合法示例；明确「第一个字符是 {，最后一个字符是 }」；字段表逐项列出；空数组也给 `[]` | 仍可能加字段、写注释、围栏外说话；引擎需要解析失败重试 |
| 模型照抄示例数量 | 示例只列 1 人／1 卷／1 场 | 示例后写「这是形状示范」，并给硬数量（cast 5–7、3–5 卷共 N 章、scenes 5–9） | 仍可能只写 1 项；review/校验器要查数量 |
| 长上下文遗忘 | 只给上一章摘要和账本，不给全文 | 账本保留事实/线索/人物状态/时间线；摘要四段式；下一章目标单独给 | 语气、伏笔、非事实性细节会漂移；长篇越往后越明显 |
| 摘要误差累积 | 每章摘要 ≤300 字，误差逐章传 | 摘要只写「发生/知情/钩子/时空」；review 的 `ledgerPatch` 即时并账；确定性门槛查字数与 POV | 语义误差无法完全消除；关键事实要在账本里二次落账 |
| 审校过严 | 模型把风格选择当错误 | `severity` 三级；`note` 不触发 revise；`verdict` 只在 block 或 warn≥3 时 revise | 仍可能把「不喜欢」写成 warn；需要人工抽检 |
| 审校过松 | 长章、问题隐蔽 | 七项对账清单；要求 `where` 指到段落/原句；`fix` 必须可执行 | 模型可能编造位置；引擎需校验 `where` 是否存在 |
| 第一人称 POV 误判 | 第一人称的「我」知道自己的全部想法 | 宪法按「视角人物能感知/能知道」定义，不按人称一刀切；第一人称允许写「我」的内心 | 审校模型可能把正常内心独白标成越界 |
| 风格样本被截断 | styleGuide 接近 4000 字 | style 预算 1500，先扣 tone；`fit` 截尾并标记 | 截断可能停在句子中间；语感样本最好把最关键的一段放前面 |
| 字数/Token 换算偏差 | 中文 1 字≈1–1.5 token | maxTokens 按字数×2.2，留余量；draft 上限 16000 | 模型仍可能提前停或写到一半被截；引擎需查字数比 |
| revise 整体重写 | 模型图省事 | 明确「只动 findings」「禁止重写全章/改主线/换文风」「字数差≤10%」 | 仍可能大改；需要 diff 或字数/结构校验 |
| 账本膨胀 | 事实/线索越积越多 | ledgerText 只取 facts 40 条、open threads 20 条、characters 12 人、timeline 最近 15 条 | 早期关键事实可能被挤掉；重要事实应保留在 canonRules |
| 章节 ID 不一致 | outline 的 id 与 item id 不同 | 所有读取用 `str(ch.id)`；缺失时回退 `ch01`；前后章用 items 顺序推导 | 回退可能读错章；引擎应保证 item.id 与 outline 一致 |
| 类型漂移 | 长篇中途写成四不像 | premise/bible/outline 注入 `GENRE_PROMISE`；review 不专门查类型 | 类型承诺是软约束；需要人工或额外审校项 |

## 13. 维护约定

1. **先改契约，再改提示词**：§4.4 的字段名/格式是硬契约。要加字段，先改 architecture 和引擎校验器，再改 `jsonContract` 和本文档。
2. **11 个函数名不能变**：recipe 按名字取函数；改名会让 stage 找不到 builder。
3. **system 控制在 1200–2200 中文字符**：改 `CRAFT` 后必须重跑 §12.2，确认最短的 system 仍 ≥1200，最长的 ≤2200。
4. **draft system 不超过 2500 字符**：它同时受 §4.3 的 system 预算约束。
5. **反 AI 腔清单两处同步**：`zh.js` 的 draft system 和本文档 §8。只改一处会导致「文档说的」和「模型看到的」不一致。
6. **示例只给形状，不给数量**：任何最小示例后面都要跟一句数量硬约束，防止模型照抄 1 项。
7. **不要在提示词里做确定性检查**：字数、段落长度、对话比、AI 腔计数属于 `src/forge/**`；提示词只负责「写得好」，不负责「判得准」。
