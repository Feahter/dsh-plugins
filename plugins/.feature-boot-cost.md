# 重客户端插件启动成本：`immediately` 语义与惰性面板改造

范围：`plugins/mind-canvas`（0.3.2）、`plugins/novel-forge`（0.4.1）。未改 `index.json`，未装依赖，未 commit，版本号未动。

## 1. `immediately` 语义证据

宿主实现来自本地 app.asar（222MB），用 `npx --yes @electron/asar extract ... /tmp/asar-full` 解出后只读取证。
绝对路径记作 `ASAR=/Applications/DeepSeek Harness.app/Contents/Resources/app.asar`，下文文件均位于 `ASAR/dsh/node_modules/@deepseek-ai/...`。

### 1.1 这个 flag 唯一的消费点：boot 阶段的一次「预取」

`dsh-web-frontend/dist/assets/index--TtJvO-i.js`（页面 boot 入口）：

```js
const n=this.prefetchImmediateTier(), s=new at; this.ctx=s,
this.page.setTotal(this.manifest.plugins.length),
await n, await VZ({ctx:s,modules:this.modules,manifest:this.manifest,...})
...
async prefetchImmediateTier(){await Promise.all(this.manifest.plugins.filter(e=>e.immediately).map(e=>this.modules.prefetch(e.id).catch(t=>{})))}
```

在整个 `@deepseek-ai/*` 的 JS 里 grep `immediately`，除 `dsh-client-modules` 的解析/序列化外，只有这一处消费（其余命中都是英文注释/工具描述）。

### 1.2 `immediately:false` 时工厂什么时候注册：仍然是 boot，只是排在 `entries.start` 里

页面 boot 在 `await prefetchImmediateTier()` 之后调用 `VZ`，`VZ` 对所有插件都建入口：

```js
// dsh-web-frontend dist
await e.modules.entries.start(n, r)
```

`dsh-client-modules/lib/client.js:383` `ClientEntries.start`：

```js
return this.enqueue(async () => {
  await Promise.all(this.desired.plugins.map(async ({ id }) => {
    await this.create(loader, id);
  }));
  await loader.await();
```

`create` → `loader.create` → vendored cordis `Entry._init` 在**创建时**就 import（`cordis-plugin-loader/lib/index.js:521`）：

```js
moduleNamespace = await this.parent.tree.import(this.options.name, this.getOuterStack);
```

→ `internal.import` → `client-modules` 的 `import/arriveGraphRow/arrive`（`lib/client.js:779/896`）→ 执行 bundle、`__ModuleLoader__.load` 注册工厂。
所以 `immediately:false` 的工厂**依旧在 boot 期注册**：`prefetchImmediateTier()` 只是把 `immediately:true` 的那批提前到 `entries.start` 之前，而未标记的那批在 `entries.start` 里被同一个逻辑加载。差别是毫秒级顺序，不是「boot 不加载」。

### 1.3 依赖 `ui-sidebar` 到达后还能不能注册侧栏：能

`arriveGraphRow` 先按 `row.inject` 加载依赖行，再加载自己（`lib/client.js:779`）：

```js
for (const packageName of row.inject) {
  const dependency = this.graphRows.get(packageName);
  if (dependency !== void 0) await this.arriveDependency(row.id, dependency, [], visited);
}
await this.arrive(row);
```

之后 cordis fiber 按 `inject` 等待服务，`apply()`（注册 `sidebar.panellist` / `main`）在 `slots`、`locale` 就绪后才跑。宿主对 `inject` 的等待不依赖 `immediately`，所以置 false 不会丢侧栏——**但也没有收益，见 1.4**。

### 1.4 bundle 还会不会在 boot 阶段被下载：会，而且和 flag 无关

`dsh-client-modules/lib/index.js:726` 的 `compose()` 把**所有**非 bootstrap 插件放进同一个 application combo batch：

```js
const application = entries.filter((entry) => !bootstrapIds.has(entry.id)) ...
for (const records of partitionComboRecords(application)) artifacts.push(buildBatch("application", records, this.readSourceMap));
```

这个 batch 在 HTML 里是 preload（`lib/index.js:539` `bootInjections` 产出 `script-preload` → `dsh-host-webserver/lib/index.js:43` 渲染成 `<link rel="preload" as="script" href=...>`）。同时 `parseBootManifest` 把每个插件行的 `initialUrl` 指向这个共享 batch（`lib/client.js:159` `initialUrls.set(id, batch.url)`），`arrive()` 默认加载 `initialUrl`。因此任何一个插件的第一次 `arrive` 都会执行整个 batch、注册全部插件工厂；再加上 1.2 的 `entries.start` 会创建全部入口，**boot 期的 bundle 请求数与总字节跟 `immediately` 无关**。

### 结论（一行）

`immediately` 只是 boot 期「预取优先级」：置 false 工厂仍会在 boot 的 `entries.start` 里注册、侧栏不会丢，但共享 application batch 仍被整体预取/执行，所以把 `true` 改 `false` 对启动成本基本是空操作——不改 flag。

## 2. 选了哪个方案

**方案 B：插件内部惰性化**（没有改 `dsh.client.immediately`，保持 `true`）。

做法：把两个插件的 `client.js` 拆成

- `client.js`：首屏只注册 `sidebar.panellist` + `main` + 语言包 + 图标，通过宿主的 `require.async('./client.panel.js')` 在**面板首次挂载**时加载重实现；
- `client.panel.js`：package-local 动态 chunk（宿主模块系统的官方机制，`dsh-client-modules` 的 `CLIENT_CHUNK = /^client\.[A-Za-z0-9][A-Za-z0-9._-]*\.js$/`，chunk 路由见 `lib/index.js:984 chunkRequest`）。
- `main` 的占位组件有 `useState` + `useEffect` 挂载点：首次渲染发 `require.async`，加载完成前显示「加载画布…/加载墨炉…」；侧栏图标不依赖 chunk。

选择理由：语义证据表明改 flag 不能让 boot 少加载/少执行 bundle；真正占启动成本的是 297KB / 216KB 的模块体在 boot 期被 materialize。拆 chunk 后首屏只剩 ~11KB / ~7.5KB，重代码推迟到用户点开面板。

## 6. 未验证项

- **没有重启桌面端做真实宿主验证**：改动只在仓库里，未安装进 `~/.dsh/profiles/desktop`；真实宿主按 `/plugins/<pkg>/client.panel.js?rev=...` 提供 chunk 的路径是读源码确认的（`dsh-client-modules/lib/index.js:984-1020`），没有在运行进程里实跑。
- **没有拿到真实宿主的 boot bundle 计数**：尝试用 Playwright 打开 `http://127.0.0.1:56136` 读 `window.__DSH_BOOT__`，20s 内没有暴露该全局（headless 下桌面注入未就绪），没有继续重试；第 1 节的结论因此来自本地宿主源码，不是运行观测。
- **没有做 `immediately` 的 A/B 实测**：翻转 flag 需要改已安装 profile 并重启桌面端，超出可写范围；语义结论是源码级的。
- **首开面板的真实等待**：harness 本地 chunk 下载+执行 20.6ms；真实磁盘/HTTP/HMR 环境可能不同，没有实测。
- **HMR/watch 对 `client.panel.js` 的重建**：esbuild 构建脚本会同时写两个文件，但宿主 dev watcher 是否监听新增的 chunk 文件未验证。
- novel-forge 的 boot 期 materialize/apply 耗时没有单独打点（只测了字节与功能回归）。
