## 2. 打分公式与权重

```
score = weights.phrase * phraseScore + weights.bm25 * bm25Score
默认 weights = { phrase: 3, bm25: 1 }
```

**候选（保持 AND）**：q 按空白切 term，每个 term 必须命中。拉丁 term 拆出的多个词全都要命中（`safeStorage` → `safe` AND `storage`）；CJK term 的 bigram 任一命中即可（`热更新` → `热更`/`更新`，所以正文写「热 更新」能命中）。状态/kind/collection/tag/source 过滤与 q 为空时行为不变。

**短语分**（大小写不敏感，`raw = q.trim().toLowerCase()`）：
- q 原文命中：title +4、tags +3、path +2、preview +1（`weights.phraseField`）
- 多 term 时每个 term 再叠加：title +1.5、tags +1、path +1、preview +0.5

**BM25**（按字段，`k1 = 1.2`）：
- `idf = ln(1 + (N - df + 0.5) / (df + 0.5))`，`N` = 本次 `status` 过滤后的候选池；`df` 是变体在该池中出现的文档数
- 字段：title（`b=0.5`，权重 2）、meta = tags+collection+path（`b=0.5`，权重 1.2）、body=preview（`b=0.75`，权重 1）
- 每字段 `tf * (k1+1) / (tf + k1*(1-b+b*len/avgLen))`，`len` 是该字段分词数，`avgLen` 是本次命中集该字段平均分词数
- 变体在查询内全局去重，避免 query 重复写同一个 bigram 时重复计分

**排序**：`sort=relevance` 按 score 降序，同分按 `id` 升序；两次调用同数据同 query 结果字节一致（已测）。

## 3. 兼容性说明

- `list({})`（无 q）完全走原路径：字段集合、排序（updatedAt）、facets 都与旧实现一致；既有 46 项宿主测试中的字段白名单测试仍过。
- `list({q})` 旧字段全保留（`id,title,kind,ext,collection,tags,sourceId,storage,path,size,status,updatedAt,snippet`），hybrid 额外追加：
  - `score`（数值）
  - `scoreParts`：`{phrase,bm25,title,meta,body}`（`scoreParts:false` 或 `debug:false` 关闭）
  - `source`：文件绝对路径（note → `notes/<id>.md`；linked → 原文件；blob → 副本；无文件 null）
  - `line`：正文命中最强行号（1 基）；标题/路径命中但正文无命中 → 1；二进制 → null；`line:false` 跳过文件读取
- `list({q, mode:'keyword'})` 逐字保留旧打分与旧排序（同分 updatedAt 降序），不追加新字段；有回归测试拿旧 `scoreEntry` 的逐字副本对拍命中集合与顺序。
- `mode` 非法值按 hybrid 处理（默认）；`weights` 可单次覆盖，也可 `createLibrary(root,{searchWeights:{...}})` 设默认。
- HTTP：`GET /api/context-lib/items?mode=keyword` 可用；不传时是 hybrid。面板/工具不传 mode，自动用 hybrid。
- 数据/索引结构未改；`index.json` 未写。

## 4. 新增测试清单（`test/search-hybrid.test.mjs`，9 项）

1. **10 条 fixture 语料**：`热更新` keyword 0 → hybrid 2（标题命中第 1、正文命中第 2）；`hotReload` keyword 0 → hybrid 1，只有 reload 的干扰项不命中。
2. keyword 搜不到 / hybrid 能搜到：CJK「热 更新」被「热更新」命中、`hotReload` 拆 hot+reload 命中；并校验 `line`、绝对 `source`、snippet。
3. 精确标题命中排在正文命中之前（`scoreParts.title` 一方 >0、正文一方 =0，分数与 phrase 都更高）。
4. 确定性：同 query 两次完整结果 JSON 相等；同分两条按 id 升序。
5. `mode:'keyword'` 与旧 `scoreEntry` 副本对拍：`alpha / alpha js / js / node.js / 不存在的词 / gamma / 完全无关` 的命中集合与顺序一致；keyword 无新字段；q 为空时 hybrid/keyword 一致且字段集合与旧白名单一致。
6. `score / scoreParts / 权重`：`weights:{phrase:0,bm25:1}` 时 score==bm25，`{phrase:1,bm25:0}` 时 score==phrase；`scoreParts:false`、`line:false` 生效。
7. `createLibrary(root,{searchWeights})` 作为默认权重，单次 `weights` 覆盖。
8. kind/collection/tag/source 过滤与 facets 语义不变（facets 仍按 q 命中集、不受额外筛选影响）。
9. linked 文件：`source` 是原文件绝对路径，`line` 指向正文「热 更新」所在第 3 行。

基准脚本：`test/bench-search.mjs`（不进 CI，`npm run bench:search`）。

## 7. 未做 / 未验证 / 发现

- **未做**：不引入 embedding / 模型（按拍板先做本地打分）；不改条目结构；不改 `index.json`；不动面板 UI（面板与工具自动走 hybrid，无开关）；不做跨进程持久缓存（检索串/分词缓存只在进程内）。
- **未验证**：`source`/`line` 只对文本条目有意义，图片等二进制 line 恒为 null；未在真实桌面端进程里点开面板做人工验证，只跑了 stub host（`.verify-host.mjs` 46 项）与 store 层测试。
- **受限**：`line` 只扫文件前 64KB；正文命中若在 64KB 之后，返回 1（而不是精确行号）。索引的 `preview` 本身只有前 1200 字符，所以实际命中基本都在前 64KB。
- **性能口径**：`N`/idf 用 `status` 过滤后的池（3862 条 active），不叠加 kind/collection/tag/source 过滤；这些过滤在打分后应用（与旧 facets 语义一致）。
- **发现（不在本任务范围，未修）**：真实 `~/.dsh/context-lib/index.json` 有 **333/3862 条** entry 的 map key 与 `entry.id` 不一致。`_parseIndex` 会把这些条目判为「id 与索引键不一致」丢弃，并在 `init()` 时因 repaired 回写 index——即当前生产实例一旦加载就会丢掉这 333 条索引（原文件不动，但索引条目/手工标签会没）。本任务的基准只在临时副本里把 id 改成 key，真实文件一个字节没动；建议 lead 另开任务确认这 333 条是否需要修复或合并。
- 版本号保持 `0.2.1`，未 commit。
